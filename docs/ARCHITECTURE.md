# V1 design record

Problem: three fictional intake sources can disagree on launch date or scope. A silent winner would misstate the contract and trigger rework. This slice validates and presents evidence for a human, not an autonomous project creator.

Flow: local JSON file or bounded loopback HTTP -> strict version/field validation -> normalized candidate values -> conflicts and unresolved questions -> SQLite idempotency record -> review packet. An independent local CLI review gate selects a source per conflict and stores a version 1 decision without changing the original packet. Business logic is pure and testable; storage handles at-least-once delivery. Each packet is `needs_review`, even when sources agree.

Trade-offs: standard-library CLI and SQLite let a reviewer run the demo without SaaS credentials or Docker. The loopback-only HTTP adapter is implemented but has no authentication or TLS. No real webhook or CRM API is implemented. A separate local mock CRM projection uses the same SQLite transaction boundary and requires the version-1 reviewed packet; replay returns the same mock project. Separate tests cover duplicate delivery, event-ID payload collision, missing required field, malformed date and unknown schema/fields. No personal, employer or production customer data belongs in the fixture.

Known gaps: concurrent SQLite writes are serialized via `BEGIN IMMEDIATE`, but this has not been load-tested; no authentication, authorization, real webhook signature, metrics, authenticated reviewer identity or amendment workflow, DB migration, or disaster recovery. Do not expose the local HTTP adapter to the internet: it bounds JSON bodies at 16 KiB, has a two-second per-socket read timeout and does not log payloads, but lacks source authentication and a full deadline policy. The local review gate permits only a synthetic local mock project write after explicit source choice; it cannot authorize any real customer-system action.
